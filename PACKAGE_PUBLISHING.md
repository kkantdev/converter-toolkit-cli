 # Python Package Publishing Guide — File Toolkit CLI

This guide outlines exactly what belongs in the production Python package and what must **never** be published to the Python Package Index (PyPI).

---

## 1. Production Files to Include

When building the package for distribution, only the core application source code, package metadata, documentation, and licensing should be bundled:

| File / Folder | Purpose |
|---|---|
| `converter/` | Main Python package containing executable application logic (`__init__.py`, `cli.py`, `update.py`, `clean.py`, `image_ops.py`, `pdf_ops.py`, `doc_ops.py`) |
| `pyproject.toml` | Build system specification, package metadata, dependencies, and CLI entry points (`cv` and `ft`) |
| `README.md` | User-facing documentation displayed on PyPI homepage |
| `LICENSE` | Official Apache 2.0 License granting permissions to users |

---

## 2. Development & Local Files NOT to Publish

The following files and directories are strictly for local development, testing, and repository management. They must **never** be packaged into distributions or uploaded to PyPI:

* **Virtual Environments** (`venv/`, `.venv/`, `env/`, `test_env/`): Heavy local binaries and platform-specific Python executables.
* **Test Suites & Fixtures** (`tests/`): Test files are for developer validation and should not bloat the end-user runtime install.
* **Internal Documentation & Drafts** (`docx/`): Internal PRD, planning memory, and draft notes intended only for repository maintainers.
* **Python Bytecode & Caches** (`__pycache__/`, `*.pyc`, `*.pyo`, `*.pyd`): Dynamically generated compiled bytecode that is machine- and Python-version-specific.
* **Test & Coverage Caches** (`.pytest_cache/`, `.coverage`, `htmlcov/`, `.mypy_cache/`, `.ruff_cache/`): Internal testing runner states.
* **Build Artifacts** (`build/`, `dist/`, `*.egg-info/`, `*.egg`): Local build output directories (only the generated `.whl` and `.tar.gz` inside `dist/` are uploaded via Twine, never checked into version control or bundled into each other).
* **Environment Secrets** (`.env`, `.env.*`): API keys, tokens, or local environment variables.
* **Git Metadata** (`.git/`, `.gitignore`): Version control internals.
* **IDE & OS Files** (`.vscode/`, `.idea/`, `.DS_Store`, `Thumbs.db`, `Desktop.ini`): Local editor and operating system artifacts.
* **Temporary Office Lock Files** (`~$*`): Lock files generated by Microsoft Office when documents are open.

## 3. PyPI Publishing Workflow

> [!IMPORTANT]
> You **never** upload the project folder directly to PyPI. Instead, Python packages must first be compiled and packaged into standardized distribution archives using the `build` tool, and then uploaded using `twine`.

### Step 1: Install Modern Packaging Tools
Make sure you have up-to-date packaging tools:
```bash
pip install --upgrade build twine
```

### Step 2: Build the Distribution Archives
Run the build tool from the project root (where `pyproject.toml` resides):
```bash
python -m build
```

This generates two standardized distribution formats in a new `dist/` directory:
1. **Source Distribution (`.tar.gz`)**: e.g., `dist/file_toolkit_cli-0.1.0.tar.gz`
   - Contains source files and metadata for building on any system.
2. **Built Wheel (`.whl`)**: e.g., `dist/file_toolkit_cli-0.1.0-py3-none-any.whl`
   - Pre-built binary package ready for direct installation via `pip`.

### Step 3: Validate Distribution Files
Use `twine check` to verify that your package description and metadata conform to PyPI standards:
```bash
twine check dist/*
```

### Step 4: Upload to TestPyPI (Recommended First Step)
Before publishing live to PyPI, test your release on TestPyPI:
```bash
twine upload --repository testpypi dist/*
```

Verify installation from TestPyPI:
```bash
pip install --index-url https://test.pypi.org/simple/ --no-deps file-toolkit-cli
```

### Step 5: Upload to Production PyPI
Once verified, upload the distribution archives to the official PyPI registry:
```bash
twine upload dist/*
```

## 5. Important Distinction

It is critical to understand the three distinct layers of file control:

### 1. `.gitignore` → Controls Git / GitHub
- Dictates which files Git tracks or ignores in the Git repository.
- Prevents local caches, virtual environments, and temporary files from being committed to GitHub.
- **Does NOT** control what `pip` installs or what gets included in built `.whl` files.

### 2. `pyproject.toml` → Controls Packaging Configuration & Wheels
- Defines the build backend (`setuptools.build_meta`).
- Specifies package discovery (`tool.setuptools.packages.find`).
- Declares runtime and optional dependencies (`rich`, `Pillow`, `pypdfium2`, etc.).
- Defines executable console scripts (`cv = converter.cli:main`).
- Directly controls what is packaged into the binary `.whl` archive.

### 3. `MANIFEST.in` → Controls Source Distributions (sdist)
- Used by setuptools to explicitly include or exclude non-code files (documentation, data files, licenses) in the source distribution (`.tar.gz`).
- When modern `pyproject.toml` with `setuptools>=61.0` is used, standard files (`pyproject.toml`, `README.md`, `LICENSE`) and discovered Python packages are automatically included in the sdist. A `MANIFEST.in` can be added if you need explicit exclusions (e.g., `prune docx` or `prune tests`).

## 6. Pre-Publishing Verification Checklist

Before running `twine upload`, always inspect your built distribution archives:

- [ ] **Clean build directory**: Delete any previous `build/` and `dist/` folders before building a new release:
  ```powershell
  Remove-Item -Recurse -Force build, dist, *.egg-info -ErrorAction SilentlyContinue
  ```
- [ ] **Run a fresh build**:
  ```powershell
  python -m build
  ```
- [ ] **Inspect the Wheel contents**:
  Examine the archive to confirm only production files are included:
  ```powershell
  python -m zipfile -l dist/*.whl
  ```
  *Verify*: Should **only** contain files under `converter/` and the `.dist-info/` directory (`METADATA`, `RECORD`, `entry_points.txt`, `LICENSE`). No `venv`, `.env`, or test files!
- [ ] **Inspect the Source Archive (`.tar.gz`)**:
  ```powershell
  tar -tzf dist/*.tar.gz
  ```
  *Verify*: Ensure no virtual environment, secrets, or temporary files leaked into the source archive.
- [ ] **Twine check**:
  ```powershell
  twine check dist/*
  ```
  *Verify*: Must output `PASSED` with 0 warnings/errors.
- [ ] **Version verification**:
  Confirm the version in `converter/__init__.py` matches `pyproject.toml` (`0.1.0`). PyPI does not allow re-uploading an existing version number.
